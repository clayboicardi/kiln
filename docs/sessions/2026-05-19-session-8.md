## Discoveries (worth carrying forward to the cumulative gotcha list)

1. **kotlin-inject 0.9.x `@get:Provides protected` on constructor params** — the `@get:` site-target binds the synthetic property getter, and `protected` keeps the param out of the public API surface while still callable by the KSP-generated subclass. Both work cleanly in 0.9.0; verified by KSP output.

2. **kotlin-inject `@Scope` annotation needs explicit `@Target(CLASS, FUNCTION, PROPERTY_GETTER)`.** Without all three, scoping a `@get:Provides` constructor param fails KSP validation. The kotlin-inject Context7 corpus shows this is the canonical convention.

3. **JdbcSqliteDriver(schema = KilnDatabase.Schema)** auto-creates and migrates the schema via PRAGMA user_version on every connect. No need for the manual `KilnDatabase.Schema.create(driver)` first-run-only guard that earlier sketches (scaffold prep §8) reached for. This is SQLDelight 2.x's preferred pattern and the driver handles the version bookkeeping internally.

4. **AndroidSqliteDriver.Callback's onOpen runs on every connection open, not just first-time creation.** Putting `PRAGMA foreign_keys = ON` here (rather than in onCreate) ensures FKs stay enforced after process restarts. The Callback class extends `androidx.sqlite.db.SupportSQLiteOpenHelper.Callback`; the SupportSQLiteDatabase param is from `androidx.sqlite.db`.

5. **Value-class type-tags resolve "two bindings, same JVM type" ambiguity in kotlin-inject.** Declaring `@JvmInline value class UserDataDir(val path: Path)` and `@JvmInline value class ScanFolders(val paths: List<Path>)` makes them distinct types at the binding layer — kotlin-inject's KSP processor matches by full TypeName, so the value-class wrapper is enough disambiguation. Compile-time tag, zero runtime cost.

6. **Application.onCreate is main-thread by Android contract**, which satisfies Media3ExoPlayerImpl's constructor-on-main-thread requirement (Session 7 discovery #9). Constructing the graph in `KilnApplication.onCreate` rather than in `MainActivity.onCreate` matters because the graph's `Media3ExoPlayerImpl` provider runs eagerly when `player` is first accessed — which can be lazily, but the singleton's first instantiation needs main. Application is the safer place.

7. **`abstract val` on a kotlin-inject @Component must have a complete provider chain at KSP time.** Adding `abstract val player: PlatformPlayer` to DesktopAppGraph before JavaSoundPlayerImpl exists would fail KSP — the framework demands the chain be resolvable. Intentionally omitting the abstract member until H5 lands is the right call; the graph file's header documents the deferral.
